Foundation Module 0 · User & Authentication — Dev-Ready Spec

โมดูลผู้ใช้งานและสิทธิ์การเข้าถึง (User & Authentication)

สเปกฐานที่ต้องสร้างก่อนโมดูลอื่นทั้งหมด — ครอบคลุมบัญชีผู้ใช้ การ login สิทธิ์ตามบทบาท และจุดเชื่อมโยงกับตาราง employee ในโมดูลบุคลากรและแรงงาน ออกแบบตาราง User/Role/UserRole เอง (ไม่พึ่งตาราง AspNetUsers/AspNetRoles/AspNetUserRoles ที่ ASP.NET Core Identity สร้างให้อัตโนมัติ) จึงต้องระบุทุกฟิลด์ที่ระบบ auth ต้องใช้ไว้ในสเปกนี้ให้ครบ ไม่มีอะไร "มาฟรี" จาก framework — ออก JWT (JSON Web Token) เป็นกลไก session เพื่อรองรับทั้งเว็บ MVC และแอป Flutter ด้วยมาตรฐานเดียวกัน

ส่วนหนึ่งของ คู่มือ ERP สำหรับธุรกิจฟาร์ม อัปเดต 19 ก.ค. 2569
1. ขอบเขตและจุดเชื่อมต่อ (Scope & Integration) 2. ฟังก์ชันหลัก (Core Functions) 3. ฐานข้อมูล (Database) 4. API 5. สิทธิ์การเข้าถึง (Roles) 6. สูตรคำนวณและกฎทางธุรกิจ (Business Rules) 7. หน้าจอที่ต้องมี (Screens)
Scope & Integration

1. ขอบเขตและจุดเชื่อมต่อ (Scope & Integration Points)

โมดูลนี้เป็น "ชั้นฐาน" ที่ทุกโมดูลต้องพึ่งพา — ต้องสร้างก่อนโมดูลอื่นทั้งหมด (Phase 0) เพราะทุกหน้าจอในระบบต้องรู้ว่าใคร login อยู่และมีสิทธิ์อะไรบ้าง ไม่ได้เป็นเจ้าของข้อมูลธุรกิจของพนักงาน (นั่นเป็นของโมดูลบุคลากรและแรงงาน)

อยู่ในขอบเขต

  • สร้าง/แก้ไข/ปิดใช้งานบัญชีผู้ใช้ (ไม่ใช่ข้อมูลพนักงานเชิงธุรกิจ)
  • Login / Logout / ลืมรหัสผ่าน / เปลี่ยนรหัสผ่าน — ออกเป็น JWT access token + refresh token
  • กำหนดบทบาท (Role) ให้บัญชีผู้ใช้แต่ละคน — ฝังเป็น claim ใน JWT
  • บันทึกประวัติการ login (Phase 2)

อยู่นอกขอบเขต (อ่านข้อมูลจากโมดูลอื่น ไม่คำนวณซ้ำ)

  • ข้อมูลธุรกิจของพนักงาน (ตำแหน่ง, ค่าแรง, วันลา) เป็นของ บุคลากรและแรงงาน (employee) — โมดูลนี้แค่เก็บ FK เชื่อมไปหาเท่านั้น
  • ไม่กำหนดกฎธุรกิจเฉพาะโมดูล (เช่น ใครดูรายงานบัญชีได้) — แต่ละโมดูลอ้างอิง Role จากที่นี่ไปบังคับใช้เอง
  • ยังแนะนำให้ใช้คลาส PasswordHasher<T> ของ ASP.NET Core (ใช้แยกเดี่ยวได้ ไม่ต้องพ่วงทั้งระบบ Identity) มาช่วย hash รหัสผ่านให้ถูกต้องปลอดภัย ไม่ต้องเขียนอัลกอริทึม hash เอง
โมดูลปลายทางใช้ข้อมูลอะไรจากที่นี่Phase
ทุกโมดูล (23 โมดูล)ตรวจสอบ Role ก่อนอนุญาตเข้าถึงแต่ละหน้าจอ/ฟังก์ชันPhase 1
บุคลากรและแรงงานผูก employee.user_id เข้ากับบัญชีผู้ใช้ที่มีอยู่แล้วPhase 1
รายงานและแดชบอร์ดแสดงชื่อผู้ใช้ปัจจุบัน/ปรับ widget ตามสิทธิ์Phase 1
Core Functions

2. ฟังก์ชันหลัก (Core Functions)

ต้องทำเสร็จก่อนเริ่มโมดูลอื่นแม้แต่โมดูลเดียว เพราะทุกหน้าจอต้องมี login/สิทธิ์คุมอยู่เบื้องหลัง

MVP — ต้องมีวันแรก Phase 1

  • Login ด้วยอีเมล/ชื่อผู้ใช้ + รหัสผ่าน — ออก JWT access token + refresh token กลับไป
  • ใช้ refresh token ขอ access token ใหม่โดยไม่ต้อง login ซ้ำ
  • Logout — เพิกถอน (revoke) refresh token ทันที
  • ลืมรหัสผ่าน/รีเซ็ตผ่านอีเมล
  • เจ้าของฟาร์ม/ผู้บริหารสร้างบัญชีผู้ใช้ใหม่ให้พนักงานได้
  • กำหนด/แก้ไข Role ของแต่ละบัญชี
  • ปิดใช้งานบัญชี (ไม่ลบ) เมื่อพนักงานลาออก — เพิกถอน refresh token ทั้งหมดของบัญชีนั้นทันที

เพิ่มทีหลังได้

  • ยืนยันตัวตนสองชั้น (2FA)Phase 2
  • พนักงานขอสร้างบัญชีเอง แล้วรอผู้บริหารอนุมัติPhase 2
  • บันทึกและแสดงประวัติการ login (เวลา/อุปกรณ์/IP)Phase 2
  • Login ผ่านบัญชี Google/Microsoft (SSO)Phase 3
  • ดูรายการ session ที่ login ค้างอยู่ และบังคับ logout ระยะไกลPhase 3
Database

3. ฐานข้อมูล (Database)

ไม่ใช้ตาราง AspNetUsers/AspNetRoles/AspNetUserRoles ของ ASP.NET Core Identity — ออกแบบตาราง User/Role/UserRole เองทั้งหมด จึงต้องระบุฟิลด์ที่ปกติ Identity จะสร้างให้อัตโนมัติ (password hash, security stamp, lockout ฯลฯ) ไว้ในสเปกนี้ครบทุกฟิลด์ ไม่ให้ตกหล่น

User Phase 1

ตารางผู้ใช้ที่ออกแบบเองทั้งหมด (ไม่ใช่ AspNetUsers ของ Identity) — รวมทั้งฟิลด์ที่ปกติ Identity จะสร้างให้อัตโนมัติ (password hash, security stamp, lockout) และฟิลด์เฉพาะธุรกิจฟาร์ม ต้องมีครบทุกฟิลด์ด้านล่างนี้ ไม่มีอะไรมาให้ฟรีจาก framework

ความสัมพันธ์: หนึ่งบัญชีมีได้หลาย Role ผ่านตาราง UserRole และอาจถูกอ้างอิงจาก employee.user_id

ฟิลด์ชนิดข้อมูลเก็บอะไร
usernameข้อความ (unique)ชื่อผู้ใช้สำหรับ login
emailข้อความ (unique)อีเมลสำหรับ login/รับลิงก์รีเซ็ตรหัสผ่าน
password_hashข้อความ (text)รหัสผ่านที่ hash แล้ว — สร้างด้วย PasswordHasher<T> ของ ASP.NET Core ห้ามเก็บรหัสผ่านจริงหรือ hash เองแบบไม่มี salt
security_stampข้อความ (GUID)เปลี่ยนค่าทุกครั้งที่รหัสผ่านถูกแก้ไข ใช้ตรวจสอบว่า token เก่าควรถูกมองว่าไม่ถูกต้องแล้ว
phone_numberข้อความ (text, ว่างได้)เบอร์โทรศัพท์ (เผื่อใช้ 2FA แบบ SMS ใน Phase 2)
email_confirmedค่าจริง/เท็จ (boolean)ยืนยันอีเมลแล้วหรือยัง
lockout_endวันเวลา (timestamp, ว่างได้)ล็อกบัญชีถึงเมื่อไหร่ — ว่าง = ไม่ได้ถูกล็อก
access_failed_countตัวเลข (int)จำนวนครั้งที่ login ผิดติดต่อกัน รีเซ็ตเป็น 0 เมื่อ login สำเร็จ
two_factor_enabledค่าจริง/เท็จ (boolean)เปิดใช้ 2FA หรือยัง (Phase 2)
full_name_thข้อความ (text)ชื่อ-นามสกุลภาษาไทยสำหรับแสดงผลในระบบ
profile_image_urlข้อความ (text, ว่างได้)รูปโปรไฟล์ที่เก็บใน Azure Blob Storage
is_activeค่าจริง/เท็จ (boolean)ปิดใช้งานบัญชีได้โดยไม่ลบข้อมูล (เมื่อพนักงานลาออก)
created_atวันเวลา (timestamp)วันที่สร้างบัญชี
created_byเลขอ้างอิง (FK → User)ใครเป็นคนสร้างบัญชีนี้ให้ (ต้องเป็นเจ้าของฟาร์ม/ผู้บริหารเท่านั้น)
last_login_atวันเวลา (timestamp, ว่างได้)เวลา login ล่าสุด ใช้ตรวจสอบบัญชีที่ไม่มีการใช้งานนาน

Role Phase 1

ตารางบทบาทที่ออกแบบเอง — นิยามบทบาทที่ใช้ร่วมกันทั้ง 23 โมดูล เป็น "แหล่งความจริงเดียว" (single source of truth) ที่ทุกโมดูลอ้างอิงในหัวข้อสิทธิ์การเข้าถึงของตัวเอง

ความสัมพันธ์: many-to-many กับ User ผ่านตาราง UserRole

ฟิลด์ชนิดข้อมูลเก็บอะไร
role_nameตัวเลือกคงที่ (enum)ชื่อบทบาท เลือกได้เฉพาะ: เจ้าของฟาร์ม/ผู้บริหาร, ผู้จัดการฟาร์ม/แปลง/โรงเรือน, พนักงาน/แรงงาน, เจ้าหน้าที่ควบคุมคุณภาพ/มาตรฐาน, พนักงานขาย, ผู้ดูแลบัญชี, ผู้ตรวจประเมินภายนอก
descriptionข้อความ (text)คำอธิบายขอบเขตสิทธิ์ของบทบาทนี้โดยรวม

UserRole Phase 1

ตารางเชื่อม many-to-many ระหว่าง User กับ Role — ปกติ Identity สร้างตาราง AspNetUserRoles ให้อัตโนมัติ แต่พอออกแบบเอง ต้องสร้างตารางนี้เองด้วย

ความสัมพันธ์: composite key จาก user_id + role_id

ฟิลด์ชนิดข้อมูลเก็บอะไร
user_idเลขอ้างอิง (FK → User)บัญชีไหน
role_idเลขอ้างอิง (FK → Role)ได้รับบทบาทอะไร

RefreshToken Phase 1

เก็บ refresh token ที่ออกให้แต่ละอุปกรณ์/บัญชี เพื่อให้ "เพิกถอน" (revoke) การใช้งานได้ — JWT access token เองยกเลิกกลางทางไม่ได้ (ตรวจสอบแค่ signature+วันหมดอายุ) จึงต้องมีตารางนี้ควบคุมชั้นของ refresh token แทน

ความสัมพันธ์: ผูกกับ User หนึ่งบัญชีมีได้หลาย token (คนละอุปกรณ์/เบราว์เซอร์)

ฟิลด์ชนิดข้อมูลเก็บอะไร
user_idเลขอ้างอิง (FK → User)token นี้ออกให้บัญชีไหน
token_hashข้อความ (text, hash แล้ว)เก็บ hash ของ refresh token ไม่เก็บค่าจริงตรง ๆ (เหมือนรหัสผ่าน กันฐานข้อมูลหลุดแล้วเอาไปใช้ต่อได้)
device_infoข้อความ (text, ว่างได้)อุปกรณ์/แอปที่ขอ token นี้ (เว็บ/Flutter Android)
issued_atวันเวลา (timestamp)วันที่ออก token
expires_atวันเวลา (timestamp)วันหมดอายุ (แนะนำ 7-30 วัน)
is_revokedค่าจริง/เท็จ (boolean)ถูกเพิกถอนแล้วหรือยัง (ตอน logout/เปลี่ยนรหัสผ่าน/ปิดบัญชี)

LoginAuditLog Phase 2

ประวัติการ login แต่ละครั้ง ใช้ตรวจสอบความปลอดภัยและสืบสวนกรณีมีปัญหา

ความสัมพันธ์: ผูกกับ User

ฟิลด์ชนิดข้อมูลเก็บอะไร
user_idเลขอ้างอิง (FK → User)ใคร login
login_atวันเวลา (timestamp)เวลาที่พยายาม login
ip_addressข้อความ (text)IP ที่ใช้ login
device_infoข้อความ (text)อุปกรณ์/เบราว์เซอร์ที่ใช้ login
is_successค่าจริง/เท็จ (boolean)login สำเร็จหรือรหัสผ่านผิด

หมายเหตุ: เนื่องจากไม่ใช้ AspNetUsers ของ Identity ฟิลด์ password_hash, security_stamp, lockout_end, access_failed_count ในตาราง User ด้านบนคือส่วนที่ปกติ Identity จะสร้างให้อัตโนมัติ — ตอนนี้ต้อง migrate/สร้างเองทั้งหมด ยังแนะนำใช้คลาส PasswordHasher<T> ของ ASP.NET Core ช่วย hash รหัสผ่านอยู่ดี (ใช้แยกเดี่ยวได้โดยไม่ต้องติดตั้งทั้งระบบ Identity) ส่วน JWT access token เองไม่มีตารางเก็บ (เป็น stateless เข้ารหัสลงในตัว token เอง) มีแค่ RefreshToken ที่ต้องเก็บไว้ควบคุมการเพิกถอน

API

4. API

Endpoint หลักที่ต้องมีสำหรับ MVP (Phase 1) และที่ตามมาใน Phase 2 — ใช้ Identity ตรวจสอบรหัสผ่านเบื้องหลัง แต่เขียน endpoint auth เองเพื่อออก JWT แทน cookie ที่ Identity ให้มา default

MethodEndpointคำอธิบายPhase
POST/auth/loginตรวจรหัสผ่านผ่าน Identity แล้วออก access token + refresh token กลับไป — ตรวจสอบจาก User (username/email, password_hash) แล้วบันทึกลง RefreshToken1
POST/auth/refresh-tokenใช้ refresh token ที่ยังไม่หมดอายุ/ไม่ถูกเพิกถอน ขอ access token ใหม่ — ตรวจสอบจาก RefreshToken (token_hash, is_revoked, expires_at) และดึง Role ที่เกี่ยวข้องจาก User/UserRole เพื่อออก access token ใหม่1
POST/auth/logoutเพิกถอน (revoke) refresh token ของอุปกรณ์นี้ทันที — บันทึกลง RefreshToken (ตั้ง is_revoked = true)1
POST/auth/forgot-passwordขอลิงก์รีเซ็ตรหัสผ่านทางอีเมล — ดึงจาก User (ตรวจสอบว่ามีอีเมลนี้อยู่จริง) ส่วนตัวลิงก์/reset token ที่ส่งออกไปยังไม่มี entity เก็บในสเปกนี้ (ยังไม่มี entity นี้ในสเปกนี้ ต้องเพิ่ม)1
POST/auth/reset-passwordตั้งรหัสผ่านใหม่จากลิงก์ที่ได้รับ แล้วเพิกถอน refresh token เดิมทั้งหมด — ตรวจสอบ reset token จากลิงก์ (ยังไม่มี entity นี้ในสเปกนี้ ต้องเพิ่ม ดู /auth/forgot-password) แล้วบันทึกลง User (password_hash, security_stamp ใหม่) และบันทึกลง RefreshToken (เพิกถอนทั้งหมดของบัญชีนั้น)1
GET/usersดึงรายชื่อผู้ใช้ทั้งหมด (เฉพาะเจ้าของ/ผู้บริหาร) — ดึงจาก User และ Role ผ่าน UserRole เพื่อแสดงบทบาทของแต่ละคน1
POST/usersสร้างบัญชีผู้ใช้ใหม่ — บันทึกลง User (อ้างอิง created_by จาก User ผู้สร้างบัญชีนี้เอง)1
PATCH/users/{id}แก้ไขข้อมูล/ปิดใช้งานบัญชี — ปิดใช้งานแล้วเพิกถอน refresh token ทั้งหมดของบัญชีนั้นด้วย — บันทึกลง User (เช่น is_active) และถ้าปิดใช้งานให้บันทึกลง RefreshToken (เพิกถอน is_revoked ทั้งหมดของ user_id นั้น)1
POST/users/{id}/assign-roleกำหนด/เปลี่ยน Role ของบัญชี — บันทึกลง UserRole (อ้างอิง user_id จาก User และ role_id จาก Role)1
GET/users/{id}/login-historyดูประวัติการ login ของบัญชีนี้ — ดึงจาก LoginAuditLog2
Roles & Permissions

5. สิทธิ์การเข้าถึง (Roles & Permissions)

โมดูลนี้เป็นแหล่งนิยาม Role ที่ทุกโมดูลอื่นในระบบอ้างอิงใช้ — ใครทำอะไรได้บ้าง "ในโมดูลนี้เอง" (จัดการบัญชีผู้ใช้) เท่านั้น ไม่ใช่สิทธิ์ในโมดูลธุรกิจอื่น

เจ้าของฟาร์ม / ผู้บริหาร

Business Rules & Formulas

6. สูตรคำนวณและกฎทางธุรกิจ (Business Rules & Formulas)

ตรรกะที่ dev ต้อง implement จริงเบื้องหลัง entity/endpoint ด้านบน

เชื่อมโยงบัญชีผู้ใช้กับพนักงาน (Optional Link)

Phase 1

ไม่ใช่ทุกบัญชีผู้ใช้ต้องเป็น employee และไม่ใช่ทุก employee ต้องมีบัญชีผู้ใช้

employee.user_id = FK -> User.Id (ว่างได้)

พนักงานที่ต้อง login เข้าระบบเอง
  -> ผูก user_id เข้ากับบัญชีที่สร้างไว้
พนักงานที่ไม่ต้อง login (เช่น แรงงานรายวัน)
  -> ปล่อย user_id เป็นค่าว่าง ไม่กระทบระบบ

ล็อกบัญชีชั่วคราวหลัง login ผิดซ้ำ (Account Lockout)

Phase 1

ต้อง implement เอง (ไม่มี Identity ทำให้อัตโนมัติแล้ว) โดยใช้ฟิลด์ access_failed_count และ lockout_end ในตาราง User

ทุกครั้งที่ login ผิด:
  access_failed_count += 1
  ถ้า access_failed_count >= 5
    -> lockout_end = now() + 5 นาที
ทุกครั้งที่ login สำเร็จ:
  access_failed_count = 0, lockout_end = null

ก่อนตรวจรหัสผ่านทุกครั้ง:
  ถ้า lockout_end != null AND lockout_end > now()
    -> ปฏิเสธ login ทันที แจ้งอีกกี่นาทีถึงจะลองใหม่ได้ (ไม่ต้องเช็ครหัสผ่านด้วยซ้ำ)

ปิดใช้งานบัญชีไม่ใช่การลบ (Soft Deactivation)

Phase 1

รักษาความสัมพันธ์ของข้อมูลเดิม (เช่น "ใครสร้างรายการนี้") แม้พนักงานคนนั้นจะออกจากงานแล้ว

เมื่อพนักงานลาออก:
  is_active = false (ห้ามลบ User ทิ้ง)
  -> ห้าม login ได้อีก แต่ประวัติ/รายการที่เคยสร้างไว้ยังอ้างอิงชื่อได้ปกติ
  -> เพิกถอน RefreshToken ทุกตัวของบัญชีนี้ทันที (is_revoked = true ทุกแถว)
  -> ถ้าผูกกับ employee ไว้ สถานะ employee ก็ต้องปิดคู่กัน (เรียกจากโมดูล HR)

อายุและการเพิกถอน JWT (Token Expiry & Revocation)

Phase 1

Access token อายุสั้นโดยตั้งใจ เพื่อจำกัดความเสียหายถ้า token หลุด — refresh token คือตัวที่คุมการเพิกถอนจริง

access_token: อายุ 15-60 นาที
  ฝัง claim: user_id, role, full_name_th
  ตรวจสอบด้วย signature เท่านั้น (ไม่ query DB ทุก request)

refresh_token: อายุ 7-30 วัน
  เก็บเป็น token_hash ใน RefreshToken table เท่านั้น (ไม่เก็บค่าจริง)
  ทุกครั้งที่ใช้ขอ access token ใหม่ -> ต้อง query DB เช็ค is_revoked/expires_at

เพิกถอน refresh token ทันทีเมื่อ:
  logout, เปลี่ยนรหัสผ่าน, ปิดใช้งานบัญชี, หรือแอดมินสั่งเพิกถอนเอง

สิทธิ์การมอบหมาย Role (Role Assignment Rule)

Phase 1

ป้องกันไม่ให้ผู้ใช้ทั่วไปยกระดับสิทธิ์ตัวเองได้

ถ้า current_user.role != เจ้าของฟาร์ม/ผู้บริหาร
  -> ปฏิเสธคำขอ assign-role ทุกกรณี แม้จะพยายามกำหนดให้ตัวเอง

นโยบายความยาว/ความซับซ้อนรหัสผ่าน

Phase 1

ตั้งค่าผ่าน Identity Password Options ไม่ต้อง validate เอง

รหัสผ่านต้องมีอย่างน้อย 8 ตัวอักษร
  ผสมตัวเลขและตัวอักษรอย่างน้อย 1 ตัวแต่ละแบบ
  (ปรับความเข้มงวดเพิ่มได้ภายหลังผ่านการตั้งค่า Identity)
Screens

7. หน้าจอที่ต้องมี (Screens/Pages)

รายชื่อหน้าจอที่ต้องมีจริงในโมดูลนี้ พร้อมส่วนประกอบหลักของแต่ละหน้า — ใช้เป็น checklist ออกแบบ UI ต่อได้ตรง ๆ ไม่ต้องนั่งไล่จากฟังก์ชัน/entity เอง

เข้าสู่ระบบ (Login) Phase 1

หน้าแรกที่ทุกคนต้องผ่านก่อนใช้งานระบบ ไม่ว่าจะเป็นเว็บ MVC หรือแอป Flutter

  • ฟอร์ม username/email + password พร้อมปุ่ม "เข้าสู่ระบบ" เรียก POST /auth/login เพื่อขอ access token + refresh token
  • ลิงก์ "ลืมรหัสผ่าน?" ไปหน้า Forgot Password
  • ข้อความแจ้งเตือนบัญชีถูกล็อกชั่วคราวเมื่อ lockout_end ยังไม่ผ่าน พร้อมนับเวลาที่เหลือ ไม่ต้องกรอกรหัสผ่านซ้ำจนกว่าจะหมดเวลา

ลืมรหัสผ่าน (Forgot Password) Phase 1

ขอลิงก์รีเซ็ตรหัสผ่านทางอีเมลเมื่อจำรหัสผ่านเดิมไม่ได้

  • ฟอร์มกรอก email เรียก POST /auth/forgot-password
  • ข้อความยืนยัน "ส่งลิงก์แล้วถ้ามีอีเมลนี้ในระบบ" — ไม่เปิดเผยว่ามี email นี้อยู่จริงหรือไม่

ตั้งรหัสผ่านใหม่ (Reset Password) Phase 1

ตั้งรหัสผ่านใหม่จากลิงก์ในอีเมล แล้วเพิกถอน refresh token เดิมทั้งหมดทันที

  • ฟอร์มรหัสผ่านใหม่ + ยืนยันรหัสผ่าน ตรวจนโยบายอย่างน้อย 8 ตัวอักษร ผสมตัวเลข/ตัวอักษร เรียก POST /auth/reset-password
  • คำเตือนว่าอุปกรณ์ที่ login ค้างอยู่ทั้งหมด (RefreshToken ทุกแถวของบัญชีนี้) จะถูก revoke ทันทีหลังตั้งรหัสผ่านใหม่สำเร็จ

รายชื่อผู้ใช้งาน (User List) Phase 1

เจ้าของฟาร์ม/ผู้บริหารดูและจัดการบัญชีผู้ใช้ทั้งหมดในระบบ

  • ตารางรายการจาก GET /users — คอลัมน์ username, full_name_th, email, Role (ผ่าน UserRole), is_active
  • ตัวกรองตาม role_name และสถานะ is_active (ใช้งาน/ปิดใช้งาน)
  • ปุ่ม "สร้างบัญชีใหม่" เปิดฟอร์มสร้างบัญชี (POST /users)
  • คลิกแต่ละแถวเข้าหน้ารายละเอียดบัญชีผู้ใช้

สร้าง/แก้ไขบัญชีผู้ใช้ (User Create/Edit Form) Phase 1

กรอกข้อมูลบัญชีใหม่ให้พนักงาน หรือแก้ไขบัญชีเดิม

  • ฟิลด์ username, email, full_name_th, phone_number
  • ดรอปดาวน์เลือก Role — บันทึกด้วย POST /users/{id}/assign-role
  • ปุ่มบันทึกเรียก POST /users (สร้างใหม่) หรือ PATCH /users/{id} (แก้ไข/ปิดใช้งาน)

รายละเอียดบัญชีผู้ใช้ (User Detail) Phase 1

ดูข้อมูลครบของบัญชีหนึ่งคนก่อนแก้ไขหรือปิดใช้งาน

  • แสดง created_at, created_by, last_login_at, email_confirmed, is_active ปัจจุบัน
  • ปุ่ม "ปิดใช้งานบัญชี" พร้อม confirm dialog — PATCH is_active=false แล้วเพิกถอน RefreshToken ทุกตัวของบัญชีนี้
  • ลิงก์ไปหน้า "ประวัติการเข้าสู่ระบบ" ของบัญชีนี้ (Phase 2)

โปรไฟล์ของฉัน (My Profile) Phase 1

ผู้ใช้ทุกคนแก้ไขข้อมูลส่วนตัวและเปลี่ยนรหัสผ่านของตัวเอง

  • ฟอร์มแก้ไข full_name_th, phone_number, profile_image_url (อัปโหลดรูปเก็บใน Azure Blob Storage)
  • ฟอร์มเปลี่ยนรหัสผ่าน (รหัสเดิม + รหัสใหม่) — เปลี่ยนแล้ว security_stamp ต้องเปลี่ยนตามทันที

บทบาทในระบบ (Roles) Phase 1

ดูรายชื่อ 7 บทบาทที่กำหนดไว้และขอบเขตสิทธิ์ของแต่ละบทบาท ใช้อ้างอิงตอนมอบหมาย Role

  • รายการ Role พร้อม description อธิบายขอบเขตสิทธิ์ (role_name เป็น enum คงที่ แก้ไม่ได้จากหน้านี้)
  • จำนวนผู้ใช้ที่ถือแต่ละ Role อยู่ (นับจากตาราง UserRole)

ประวัติการเข้าสู่ระบบ (Login History) Phase 2

ตรวจสอบความปลอดภัยจากประวัติการ login ของบัญชีหนึ่งคน

  • ตารางจาก GET /users/{id}/login-history — login_at, ip_address, device_info, is_success (badge เขียว/แดง)
  • ตัวกรองช่วงวันที่ และสวิตช์ดูเฉพาะรายการ login ที่ล้มเหลว (is_success = false)

ยืนยันตัวตนสองชั้น (2FA Setup) Phase 2

ผู้ใช้เปิด/ปิดการยืนยันตัวตนสองชั้นของบัญชีตัวเอง

  • สวิตช์เปิด/ปิด two_factor_enabled พร้อมฟอร์มยืนยัน phone_number ก่อนเปิดใช้งานจริง
  • ขั้นตอนกรอกรหัส OTP ที่ส่งไปยัง phone_number เพื่อยืนยันก่อนบันทึก

คำขอสร้างบัญชีรออนุมัติ (Pending Signup Approval) Phase 2

ผู้บริหารอนุมัติหรือปฏิเสธบัญชีที่พนักงานขอสร้างเอง

  • รายการคำขอพร้อมข้อมูลที่กรอกไว้: username, email, full_name_th
  • ปุ่ม "อนุมัติ" (ตั้ง is_active=true แล้วเปิดฟอร์มมอบหมาย Role ต่อ) และปุ่ม "ปฏิเสธ"

เข้าสู่ระบบผ่าน SSO (SSO Login) Phase 3

ทางเลือกเข้าสู่ระบบด้วยบัญชี Google/Microsoft แทนรหัสผ่านของระบบเอง

  • ปุ่ม "เข้าสู่ระบบด้วย Google" / "เข้าสู่ระบบด้วย Microsoft" บนหน้า Login เดิม
  • หน้าจับคู่บัญชี SSO เข้ากับ User ที่มีอยู่แล้วโดยเทียบจาก email

Session ที่ใช้งานอยู่ (Active Sessions) Phase 3

ดูอุปกรณ์ที่ login ค้างอยู่ทั้งหมดของบัญชีตัวเอง และบังคับออกจากระบบระยะไกล

  • ตารางรายการ RefreshToken ที่ is_revoked=false — device_info, issued_at, expires_at
  • ปุ่ม "ออกจากระบบอุปกรณ์นี้" ต่อแถว — ตั้ง is_revoked=true ทันที
เอกสารนี้เป็นสเปกเริ่มพัฒนาโมดูล "ผู้ใช้งานและสิทธิ์การเข้าถึง" ต้องสร้างเป็นลำดับแรกก่อนโมดูลอื่นทั้งหมด ← กลับไปภาพรวม ERP ฟาร์ม
