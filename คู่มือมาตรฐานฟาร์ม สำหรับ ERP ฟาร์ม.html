โมดูลมาตรฐานฟาร์ม (Farm Standards)

สเปกสำหรับเริ่มพัฒนาได้ทันที ครอบคลุมขอบเขตและจุดเชื่อมต่อกับโมดูลอื่น ฟังก์ชันหลักแยก MVP กับที่เพิ่มทีหลังได้ โครงสร้างฐานข้อมูล API หลักที่ต้องมี สิทธิ์การเข้าถึงตามบทบาท และสูตรคำนวณ/กฎทางธุรกิจ

ส่วนหนึ่งของ คู่มือ ERP สำหรับธุรกิจฟาร์ม อัปเดต 18 ก.ค. 2569
1. ขอบเขตและจุดเชื่อมต่อ (Scope & Integration) 2. ฟังก์ชันหลัก (Core Functions) 3. ฐานข้อมูล (Database) 4. API 5. สิทธิ์การเข้าถึง (Roles) 6. สูตรคำนวณ (Formulas)
Scope & Integration

1. ขอบเขตและจุดเชื่อมต่อ (Scope & Integration Points)

โมดูลนี้ดูแลการขอ/ต่ออายุ/รักษามาตรฐานฟาร์ม (GAP, GMP, HACCP, ปศุสัตว์ OK, Organic ฯลฯ) ตั้งแต่เช็กลิสต์ข้อกำหนด การตรวจประเมิน จนถึงติดตามใบรับรองและการแก้ไขข้อบกพร่อง โดยดึงหลักฐานจากโมดูลอื่นแทนการบันทึกซ้ำ

อยู่ในขอบเขต

  • กำหนดมาตรฐาน/เช็กลิสต์ข้อกำหนดที่ฟาร์มต้องปฏิบัติตาม
  • วางแผน/บันทึกผลการตรวจประเมิน (audit) ทั้งภายในและภายนอก
  • ติดตามข้อบกพร่องและการแก้ไข (Corrective Action)
  • ติดตามอายุใบรับรองและแจ้งเตือนก่อนหมดอายุ
  • รวบรวมหลักฐานพร้อมส่งผู้ตรวจประเมิน

อยู่นอกขอบเขต (อ่านข้อมูลจากโมดูลอื่น ไม่คำนวณซ้ำ)

  • ไม่ได้เป็นเจ้าของข้อมูลการผลิตเอง — ดึงหลักฐานจาก ตรวจสอบย้อนกลับ (trace_code/trace_link), การให้น้ำ ปุ๋ย และยา, สุขภาพและวัคซีน
  • ไม่ตรวจสอบ PHI/withdrawal period ซ้ำ — ใช้ผลจากโมดูลต้นทางที่คำนวณไว้แล้ว
  • การส่งรายงานให้หน่วยงานรัฐจริง — เป็นของ รายงานหน่วยงานรัฐ
โมดูลต้นทางข้อมูลที่ดึงมาใช้ทำอะไรใน Farm StandardsPhase
ตรวจสอบย้อนกลับtrace_code, trace_link ของรอบผลิต/lot ที่ตรวจเป็นหลักฐานประกอบเช็กลิสต์ (evidence pack)Phase 2
การให้น้ำ ปุ๋ย และยาpesticide_application, ผล PHI checkหลักฐานการใช้สารเคมีตามเกณฑ์ GAPPhase 2
สุขภาพและวัคซีนvaccination_record, treatment_record, ผล withdrawal checkหลักฐานตามเกณฑ์ปศุสัตว์ OK/GMPPhase 2
ผังแปลงและที่ดิน / ทะเบียนสัตว์field, animal_group ที่อยู่ในขอบเขตการรับรองระบุขอบเขตพื้นที่/กลุ่มสัตว์ที่ใบรับรองครอบคลุมPhase 1
รายงานและแดชบอร์ดสถานะใบรับรอง, ผล auditแสดงในแดชบอร์ดภาพรวมPhase 2
Core Functions

2. ฟังก์ชันหลัก (Core Functions)

แยกชัดว่าอะไรต้องใช้งานได้ตั้งแต่วันแรก (MVP) และอะไรเพิ่มทีหลังได้โดยไม่กระทบการรักษามาตรฐานพื้นฐาน

MVP — ต้องมีวันแรก Phase 1

  • กำหนดมาตรฐาน/เวอร์ชันเช็กลิสต์ที่ฟาร์มต้องปฏิบัติตาม
  • บันทึกแผนและผลการตรวจประเมิน (audit) ต่อมาตรฐาน
  • บันทึกผลรายข้อของเช็กลิสต์ (ผ่าน/ไม่ผ่าน/ไม่เกี่ยวข้อง)
  • เปิดและติดตามข้อบกพร่อง/การแก้ไขจนปิดงาน
  • บันทึกใบรับรอง วันออก วันหมดอายุ และแจ้งเตือนล่วงหน้า

เพิ่มทีหลังได้

  • ดึงหลักฐานอัตโนมัติจากตรวจสอบย้อนกลับ/โมดูลอื่นมาแปะในเช็กลิสต์Phase 2
  • วิเคราะห์แนวโน้มผลตรวจประเมินย้อนหลังPhase 2
  • พอร์ทัลให้ผู้ตรวจประเมินภายนอกเข้าดู/คอมเมนต์เองPhase 3
  • เซ็นเอกสารรับรองด้วยลายเซ็นดิจิทัลPhase 3
Database

3. ฐานข้อมูล (Database)

แต่ละเอนทิตีคือ 1 ตารางในฐานข้อมูล พร้อมคำอธิบายว่าแทนอะไรในโลกจริง และแต่ละฟิลด์เก็บอะไร ชนิดข้อมูลแบบไหน

certification_standard Phase 1

มาตรฐานรับรอง — นิยามของมาตรฐานที่ฟาร์มต้องการขอ/รักษา เช่น GAP, GMP, HACCP, ปศุสัตว์ OK, Organic

ความสัมพันธ์: เป็นต้นทางของ standard_checklist_item, audit_record, certificate

ฟิลด์ชนิดข้อมูลเก็บอะไร
standard_nameตัวเลือกคงที่ (enum)ชื่อมาตรฐาน เลือกได้เฉพาะ: GAP, GMP, HACCP, ปศุสัตว์_OK, Organic, อื่นๆ
versionข้อความ (text)เวอร์ชัน/ปีของเกณฑ์มาตรฐานที่ใช้อ้างอิง
issuing_bodyข้อความ (text)หน่วยงานที่ออกใบรับรอง เช่น กรมวิชาการเกษตร กรมปศุสัตว์
scope_typeตัวเลือกคงที่ (enum)ใช้กับพืชหรือปศุสัตว์ เลือกได้เฉพาะ: crop, livestock, both
audit_cycle_monthsตัวเลข (int)รอบระยะเวลาที่ต้องตรวจประเมินซ้ำ หน่วยเดือน

standard_checklist_item Phase 1

ข้อกำหนดในเช็กลิสต์ — รายการข้อกำหนดย่อยของมาตรฐานหนึ่งที่ต้องตรวจสอบทุกครั้งที่มี audit

ความสัมพันธ์: ผูกกับ certification_standard หนึ่งรายการมีได้หลายข้อกำหนด

ฟิลด์ชนิดข้อมูลเก็บอะไร
standard_idเลขอ้างอิง (FK → certification_standard)ข้อกำหนดนี้เป็นของมาตรฐานไหน
item_codeข้อความ (text)รหัสข้อกำหนดตามเอกสารมาตรฐาน เช่น "GAP-4.2"
requirement_textข้อความ (text)รายละเอียดสิ่งที่ต้องปฏิบัติตาม
evidence_type_requiredข้อความ (text, ว่างได้)ประเภทหลักฐานที่ต้องแนบ เช่น "บันทึกการใช้สารเคมี"
is_criticalค่าจริง/เท็จ (boolean)เป็นข้อกำหนดวิกฤต ถ้าไม่ผ่านให้ audit ล้มเหลวทันทีหรือไม่

audit_record Phase 1

รอบการตรวจประเมิน — บันทึกการตรวจประเมินหนึ่งครั้งของมาตรฐานหนึ่ง ไม่ว่าจะเป็นการตรวจภายในเองหรือผู้ตรวจภายนอก

ความสัมพันธ์: ผูกกับ certification_standard และมี audit_finding ย่อยหลายรายการ

ฟิลด์ชนิดข้อมูลเก็บอะไร
standard_idเลขอ้างอิง (FK → certification_standard)รอบตรวจนี้เป็นของมาตรฐานไหน
audit_dateวันที่ (date)วันที่ตรวจประเมิน
audit_typeตัวเลือกคงที่ (enum)เลือกได้เฉพาะ: internal (ตรวจเอง), external (ผู้ตรวจภายนอก)
auditor_nameข้อความ (text)ชื่อผู้ตรวจ/หน่วยงานผู้ตรวจ
overall_resultตัวเลือกคงที่ (enum)ผลรวม เลือกได้เฉพาะ: pass, conditional, fail — คำนวณจาก audit_finding
next_audit_due_dateวันที่ (date)วันครบกำหนดตรวจครั้งถัดไป

audit_finding Phase 1

ผลตรวจรายข้อ — ผลการตรวจของแต่ละข้อกำหนดในเช็กลิสต์ ณ รอบ audit หนึ่ง พร้อมการแก้ไขถ้าพบข้อบกพร่อง

ความสัมพันธ์: ผูกกับ audit_record และ standard_checklist_item

ฟิลด์ชนิดข้อมูลเก็บอะไร
audit_record_idเลขอ้างอิง (FK → audit_record)ผลนี้เป็นของรอบตรวจไหน
checklist_item_idเลขอ้างอิง (FK → standard_checklist_item)ผลนี้เป็นของข้อกำหนดไหน
resultตัวเลือกคงที่ (enum)เลือกได้เฉพาะ: comply, non_comply, not_applicable
evidence_refข้อความ (text, ว่างได้)อ้างอิงหลักฐาน เช่น trace_code หรือไฟล์แนบ
corrective_actionข้อความ (text, ว่างได้)สิ่งที่ต้องแก้ไข ถ้าผลเป็น non_comply
corrective_deadlineวันที่ (date, ว่างได้)กำหนดเวลาต้องแก้ไขให้เสร็จ
corrective_statusตัวเลือกคงที่ (enum, ว่างได้)เลือกได้เฉพาะ: open, in_progress, closed

certificate Phase 1

ใบรับรอง — เอกสารใบรับรองที่ออกจริงหลังผ่านการตรวจประเมิน พร้อมวันหมดอายุที่ต้องเฝ้าติดตาม

ความสัมพันธ์: ผูกกับ certification_standard และอาจอ้างอิง audit_record ที่ทำให้ได้ใบรับรองนี้

ฟิลด์ชนิดข้อมูลเก็บอะไร
standard_idเลขอ้างอิง (FK → certification_standard)ใบรับรองนี้เป็นของมาตรฐานไหน
audit_record_idเลขอ้างอิง (FK → audit_record, ว่างได้)ออกจากผลตรวจรอบไหน
certificate_numberข้อความ (unique)เลขที่ใบรับรองตามที่หน่วยงานออกให้
issued_dateวันที่ (date)วันที่ออกใบรับรอง
expiry_dateวันที่ (date)วันหมดอายุใบรับรอง
statusตัวเลือกคงที่ (enum)เลือกได้เฉพาะ: active, expiring_soon, expired, revoked
file_refข้อความ (text)ตำแหน่งที่เก็บไฟล์สแกนใบรับรอง

Business Rules & Formulas

6. สูตรคำนวณและกฎทางธุรกิจ (Business Rules & Formulas)

ตรรกะที่ dev ต้อง implement จริงเบื้องหลัง entity/endpoint ด้านบน

ตัดสินผลรวมของ Audit (Overall Result Determination)

Phase 1

คำนวณจากสัดส่วนข้อกำหนดที่ผ่าน เมื่อบันทึก audit_finding ครบทุกข้อ

compliance_pct =
  จำนวนข้อที่ result = comply
  / จำนวนข้อทั้งหมดที่ result != not_applicable
  × 100

ถ้ามีข้อ critical ใดข้อหนึ่ง result = non_comply
  -> overall_result = fail
ถ้า compliance_pct >= 95%
  -> overall_result = pass
ถ้า 80% <= compliance_pct < 95%
  -> overall_result = conditional (ต้องมี corrective_action)
ถ้า compliance_pct < 80%
  -> overall_result = fail

กำหนดวันตรวจครั้งถัดไป (Next Audit Due Date)

Phase 1

ตั้งอัตโนมัติทันทีที่บันทึกผล audit เสร็จ ใช้แจ้งเตือนล่วงหน้า

next_audit_due_date =
  audit_date + standard.audit_cycle_months (เดือน)

ถ้า overall_result = fail
  -> next_audit_due_date = audit_date + 1 เดือน (ตรวจซ้ำเร็วขึ้น)

แจ้งเตือนใบรับรองใกล้หมดอายุ (Certificate Expiry Alert)

Phase 1

รันเป็น scheduled job ตรวจทุกวัน เทียบกับวันที่ปัจจุบัน

days_remaining = expiry_date - today

ถ้า days_remaining <= 0
  -> status = expired
ถ้า 0 < days_remaining <= 60
  -> status = expiring_soon -> แจ้งเตือนผู้รับผิดชอบ
ถ้า days_remaining > 60
  -> status = active

ทวงติดตามการแก้ไข (Corrective Action Escalation)

Phase 1

ป้องกันข้อบกพร่องค้างเกินกำหนดโดยไม่มีใครติดตาม

ถ้า corrective_status != closed
  AND today > corrective_deadline
  -> แจ้งเตือนผู้จัดการพื้นที่และเจ้าหน้าที่มาตรฐานทันที
     (escalate เป็นรายวันจนกว่าจะปิดงาน)

ดึงหลักฐานอัตโนมัติจากตรวจสอบย้อนกลับ (Evidence Auto-Pull)

Phase 2

ลดงานคีย์ซ้ำโดยดึง evidence_ref จากข้อมูลที่มีอยู่แล้วในระบบ

เมื่อสร้าง audit_finding ที่ evidence_type_required ตรงกับ
  ประเภทข้อมูลใน trace_link (source_module = crop/livestock)
  ของช่วงเวลาเดียวกัน
  -> เสนอ evidence_ref อัตโนมัติให้ผู้ตรวจเลือกยืนยัน
