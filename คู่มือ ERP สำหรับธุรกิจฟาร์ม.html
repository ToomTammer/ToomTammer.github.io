Farm Business · ERP Requirements

ระบบ ERP สำหรับธุรกิจฟาร์ม (Farm ERP System)

รายการโมดูลและฟีเจอร์ที่ควรมี ครอบคลุมทั้งฟาร์มปศุสัตว์ พืชไร่/พืชสวน และฟาร์มผสมผสาน — เลือกเฉพาะส่วนที่ตรงกับธุรกิจจริง แล้วตัดส่วนที่ไม่เกี่ยวข้องออก

เอกสารประกอบการวางแผนระบบ อัปเดต 18 ก.ค. 2569
โมดูลหลัก (Core Modules) ปศุสัตว์ (Livestock) พืชไร่/พืชสวน (Crop) ตรวจสอบย้อนกลับ (Traceability) โครงสร้างพื้นฐาน (Infrastructure) ลำดับการทำ (Rollout Plan)

Technical Requirements

5. ข้อกำหนดด้านเทคนิคและโครงสร้างพื้นฐาน (Technical & Infrastructure Requirements)

สแตกที่เลือกจริงสำหรับเริ่มพัฒนา — เลือกให้เหมาะกับทีมพัฒนาคนเดียว (.NET dev, ไม่มีทีม IT) และงบประมาณเริ่มต้นของธุรกิจใหม่ โดยยังรักษาทางเลือกย้ายกลับ on-premise ไว้ได้ในอนาคตตามนโยบายบริษัท

ระบบหลังบ้านและ API (Backend & API)

  • ASP.NET Core Web API + Entity Framework Core
  • สิทธิ์การเข้าถึง: ASP.NET Core Identity (role-based)
  • งาน background/สูตรคำนวณตามกำหนดเวลา (เช่น แจ้งเตือนใบรับรองหมดอายุ, คำนวณ FCR/THI): Hangfire ฝังในแอปเดียวกัน

หน้าเว็บ/แดชบอร์ด (Web & Dashboard)

  • .NET MVC สำหรับใช้งานฝั่งสำนักงาน
  • กราฟ/แดชบอร์ด: Chart.js หรือ ApexCharts ฝังในแอปเดียวกัน (ไม่ใช้บริการ BI แยกต่างหาก)

แอปภาคสนาม (Field App, offline-first)

  • Flutter — รองรับเฉพาะ Android เท่านั้น เพื่อลดความซับซ้อนและค่าใช้จ่ายด้าน iOS
  • เครื่องเป็นของบริษัทจัดซื้อแจกพนักงาน (ไม่ใช่ BYOD) ควบคุมรุ่น/เวอร์ชันได้ง่ายกว่า
  • แจกแอปผ่านไฟล์ APK โดยตรง ไม่ผ่าน Google Play

ฐานข้อมูลและไฟล์ (Database & Storage)

  • Azure SQL Database — จับคู่กับ EF Core ได้ลื่นสุด มี backup อัตโนมัติในตัว
  • ไฟล์ (QR code, ใบรับรอง, PDF): Azure Blob Storage

การติดตั้งและ CI/CD (Hosting & CI/CD)

  • Azure App Service — deploy โค้ดตรง (native) ไม่ใช้ Docker ในช่วงเริ่มต้น เพื่อความง่ายสุดสำหรับคนดูแลคนเดียว
  • CI/CD: GitHub Actions — push โค้ดแล้ว deploy อัตโนมัติ

สิทธิ์และความปลอดภัย (Access & Security)

  • กำหนดสิทธิ์ตามบทบาท (role-based access) ผ่าน ASP.NET Core Identity
  • Azure SQL Database สำรองข้อมูลอัตโนมัติทุกวัน

Alternative Options Considered

ทางเลือกอื่นที่เคยพิจารณา (Alternative Options Considered)

ปรับใช้ระดับ (tier) สำหรับใช้งานจริงเท่านั้น ไม่นับ free tier/dev tier ที่ไม่มี SLA — เก็บไว้เป็นข้อมูลอ้างอิงเผื่อทบทวนใหม่ในอนาคต ปัจจุบันยังแนะนำ Azure ตามตารางค่าใช้จ่ายด้านบน

Option A

ทางเลือก A: Google Cloud Run + PostgreSQL

รายการบริการที่ใช้บาท/เดือน
1Hosting (compute)Google Cloud Run — 1 vCPU/512MiB, min-instance=1 (always-on ไม่มี cold start, ไม่นับ free tier) ~2,290
2ฐานข้อมูลCloud SQL for PostgreSQL — db-custom-1-3840 (1 vCPU dedicated, 3.75GB) + storage 20GB + public IP ~2,240
3ไฟล์ (QR/ใบรับรอง/PDF)Google Cloud Storage Standard ~35-70
4เก็บ Docker imageGoogle Artifact Registry ~18
5CI/CDGitHub Actions (โควตาฟรีถาวร ไม่ใช่ trial) — 0

รวมโดยประมาณ ~4,585-4,620 บาท/เดือน — แพงกว่า Azure ถึง ~4 เท่า เพราะราคาก่อนหน้าที่เคยเสนอ (~525-980 บาท) อิงจาก free tier/dev tier (db-f1-micro ไม่มี SLA) ซึ่งใช้งานจริงจังไม่ได้ พอปรับเป็นระดับที่มี SLA รองรับการใช้งานจริง (dedicated vCPU ทั้ง compute และ DB, ปิด cold start ด้วย min-instance=1) ราคาสูงกว่า Azure ชัดเจน เพราะ Cloud Run/Cloud SQL ไม่ได้ถูกออกแบบมาให้ถูกที่สุดตอนต้อง "เปิดทิ้งไว้ตลอด" แบบ Azure App Service

Option B

ทางเลือก B: VPS + Docker (self-managed)

รายการบริการที่ใช้บาท/เดือน
1Hosting (VPS ตัวเดียว รันทุกอย่าง)DigitalOcean CPU-Optimized Droplet 2vCPU/4GB (dedicated vCPU ไม่ใช่ shared) ~1,400
2ฐานข้อมูลPostgreSQL รันเป็น container บน VPS เดียวกัน — 0 (ใช้ทรัพยากร VPS เดิม)
3ไฟล์ + backupDigitalOcean Spaces (S3-compatible, 250GB) ~175
4เก็บ Docker imageDigitalOcean Container Registry (starter) ~175 (ข้ามได้ถ้า build ตรงบน VPS)
5CI/CDGitHub Actions (SSH deploy เข้า VPS) — 0

รวมโดยประมาณ ~1,750 บาท/เดือน — ข้อควรระวังสำคัญที่สุด: แบบนี้ไม่มี managed service ใด ๆ เลย ต้องดูแลเอง patch OS, patch PostgreSQL, ตั้ง backup เอง, จัดการ SSL certificate เอง (ใช้ Let's Encrypt ผ่าน Caddy/Nginx ได้ฟรีแต่ต้องตั้งเอง) — แพงกว่า Azure แล้วยังต้องดูแลเองทั้งหมด จึงไม่ใช่ทางเลือกที่คุ้มค่าเมื่อเทียบกับ Azure สำหรับผู้ดูแลระบบคนเดียว

Option C

ทางเลือก C: รันที่เครื่อง Local/On-Premise เอง

รายการแนวทางค่าใช้จ่าย
1ฮาร์ดแวร์ (ครั้งเดียว)เครื่อง mini PC/tower เล็กในออฟฟิศ ~15,000-40,000 บาท
2ระบบปฏิบัติการUbuntu Server (ฟรี) หรือ Windows Server (มีค่า license ~25,000 บาทครั้งเดียว)
3ฐานข้อมูลSQL Server Express — ฟรี (จำกัด 10GB ต่อฐานข้อมูล)
4ไฟล์ + สำรองข้อมูลเก็บบน disk เครื่องเดียวกัน + external HDD/NAS แยก ~3,000-10,000 บาทครั้งเดียว
5เครื่องสำรองไฟ (UPS)จำเป็น เพราะไฟดับกลางคันคือสาเหตุอันดับ 1 ที่ฐานข้อมูลพัง ~3,000-8,000 บาทครั้งเดียว
6การเข้าถึงจากภาคสนาม/นอกสถานที่Tailscale VPN (ฟรีสำหรับทีมเล็ก) — 0/เดือน
7สำรองข้อมูลนอกสถานที่ (แนะนำ)คลาวด์เก็บไฟล์ backup อย่างเดียว (เช่น Backblaze B2) ~50-200 บาท/เดือน

ค่าใช้จ่ายครั้งเดียว ~21,000-83,000 บาท (ขึ้นกับเลือก Windows Server หรือไม่) + รายเดือนแทบไม่มีเลย ~50-200 บาท/เดือน — ถูกที่สุดในระยะยาวแบบชัดเจน เพราะไม่มีค่าเช่าเซิร์ฟเวอร์รายเดือนเลย แต่ต้องดูแลเองทั้งหมดเหมือนทางเลือก B บวกความเสี่ยงเพิ่ม: ไฟดับ/เน็ตหลุด/เครื่องพัง กระทบระบบทันทีโดยไม่มี data center รองรับ และถ้าเครื่องพังโดยไม่มี backup ที่ทดสอบแล้ว ข้อมูลอาจหายถาวร — เหมาะกับกรณีที่นโยบายบริษัทต้องการ on-premise จริงจังและยอมรับความเสี่ยงนี้ได้ ไม่เหมาะถ้าต้องการความมั่นใจสูงสุดเรื่อง uptime

Option D

ทางเลือก D: App/เว็บรันที่ local — ฐานข้อมูล/ไฟล์/backup อยู่บน Cloud (Hybrid)

รายการแนวทางค่าใช้จ่าย
1ฮาร์ดแวร์ (ครั้งเดียว)เครื่อง mini PC ในออฟฟิศ รัน ASP.NET Core Web API + MVC เท่านั้น (ไม่ต้องเผื่อพื้นที่เก็บข้อมูลมาก) ~10,000-25,000 บาท
2ระบบปฏิบัติการUbuntu Server (ฟรี)
3ฐานข้อมูลAzure SQL Database Standard S0 — บนคลาวด์ ~515/เดือน
4ไฟล์ (QR/ใบรับรอง/PDF)Azure Blob Storage — บนคลาวด์ ~105-175/เดือน
5สำรองข้อมูลรวมอยู่ใน Azure SQL Database อัตโนมัติแล้ว — 0 เพิ่ม
6เครื่องสำรองไฟ (UPS)ยังแนะนำสำหรับเครื่อง local กันแอปหยุดกะทันหัน ~3,000-8,000 บาทครั้งเดียว
7CI/CDGitHub Actions + self-hosted runner ติดตั้งบนเครื่อง local (ฟรี)

ค่าใช้จ่ายครั้งเดียว ~13,000-33,000 บาท + รายเดือน ~620-690 บาท/เดือน — ถูกกว่าตารางค่าใช้จ่าย Azure หลักด้านบน (~1,080-1,150 บาท) เพราะตัดค่า Azure App Service ออก (ใช้เครื่อง local รันแทน) แต่ยังได้ backup/ความปลอดภัยของข้อมูลระดับ cloud เต็มที่ เพราะข้อมูลจริงไม่ได้อยู่ที่เครื่อง local เลย — ข้อควรระวังสำคัญที่สุด: พึ่งอินเทอร์เน็ตมากกว่าทางเลือก C (on-premise ล้วน) เพราะแม้แต่คนที่ใช้งานในออฟฟิศเองก็ต้องผ่านอินเทอร์เน็ตไปเรียก Azure SQL/Blob Storage ทุกครั้ง ถ้าเน็ตที่ฟาร์มหลุด ระบบหยุดทำงานทั้งหมดทันทีแม้จะอยู่ในพื้นที่เดียวกับเครื่อง local ก็ตาม (ต่างจากทางเลือก C ที่ยังใช้งานผ่าน LAN ภายในต่อได้ระหว่างเน็ตหลุด) เหมาะกับกรณีที่อินเทอร์เน็ตที่ฟาร์มเสถียรพอสมควร และอยากประหยัดค่าใช้จ่าย hosting โดยไม่เสียความปลอดภัยของข้อมูล
