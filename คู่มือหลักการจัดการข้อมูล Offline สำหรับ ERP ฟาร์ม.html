คู่มือหลักการจัดการข้อมูล Offline (Offline Data Management)

แนวทางออกแบบและ implement การเก็บ/ซิงค์ข้อมูลของแอปภาคสนาม (Flutter, offline-first) ให้ทำงานได้แม้ไม่มีอินเทอร์เน็ต แล้วซิงค์กับ ASP.NET Core API + Azure SQL Database ได้อย่างปลอดภัย ไม่ชนกัน ไม่ข้อมูลหาย

ส่วนหนึ่งของ คู่มือ ERP สำหรับธุรกิจฟาร์ม อัปเดต 19 ก.ค. 2569

Core Principles

1. หลักการพื้นฐาน (Core Principles)

แนวคิดหลักที่ทุกฟีเจอร์ในแอปภาคสนามต้องยึดตาม เพื่อให้พนักงานบันทึกข้อมูลได้ต่อเนื่องแม้เน็ตหลุดกลางทาง

Local-First

  • ทุกการบันทึกข้อมูลเขียนลง SQLite ในเครื่องก่อนเสมอ ไม่รอเชื่อมเน็ตก่อนบันทึก
  • ซิงค์ขึ้นเซิร์ฟเวอร์เป็นขั้นตอนที่เกิด "ทีหลัง" ไม่ใช่เงื่อนไขของการบันทึกสำเร็จ

Optimistic UI

  • ผู้ใช้เห็นข้อมูลของตัวเองทันทีที่กดบันทึก ไม่ต้องรอ round-trip ไปเซิร์ฟเวอร์
  • แสดงสถานะ "รอซิงค์" กำกับไว้ ไม่ใช่ทำให้ดูเหมือนบันทึกไม่สำเร็จ

Idempotent Sync

  • ส่งข้อมูลเดิมซ้ำไปเซิร์ฟเวอร์กี่ครั้งก็ต้องได้ผลลัพธ์เดียวกัน ไม่สร้างข้อมูลซ้ำ
  • สำคัญมากเพราะเน็ตในพื้นที่ฟาร์มหลุดกลางการส่งได้บ่อย ต้อง retry ได้อย่างปลอดภัย

Server Time is Truth

  • ใช้เวลาของเซิร์ฟเวอร์ตัดสิน conflict ไม่ใช่เวลาในเครื่องมือถือ (นาฬิกาเครื่องอาจเพี้ยน/ไม่ตรงกัน)
Sync Engine Components

2. องค์ประกอบของระบบ Sync (Sync Engine Components)

แยกชัดว่าอะไรต้องมีตั้งแต่วันแรก (MVP) และอะไรเพิ่มทีหลังได้

MVP — ต้องมีวันแรก Phase 1

  • SQLite local database เก็บข้อมูลทุกฟอร์มที่พนักงานกรอกในพื้นที่
  • ตาราง sync_queue เก็บรายการที่รอส่งขึ้นเซิร์ฟเวอร์ ตามลำดับเวลาที่เกิด
  • ตรวจจับสถานะอินเทอร์เน็ต แล้วเริ่ม sync อัตโนมัติทันทีที่กลับมาออนไลน์
  • สร้าง client-generated UUID ให้ทุกเรคคอร์ดใหม่ที่สร้างตอนออฟไลน์
  • แสดงสถานะ pending/synced/failed ต่อเรคคอร์ดในหน้า UI

เพิ่มทีหลังได้

  • Background sync อัตโนมัติเป็นช่วง ๆ แม้แอปไม่ได้เปิดอยู่หน้าจอPhase 2
  • Batch sync ส่งหลายเรคคอร์ดพร้อมกันในคำขอเดียวเพื่อลดรอบการเชื่อมต่อPhase 2
  • ลบข้อมูลเก่าที่ซิงค์แล้วออกจากเครื่องเป็นระยะ เพื่อประหยัดพื้นที่Phase 2
  • แจ้งเตือนแอดมินอัตโนมัติเมื่อพบ conflict ที่ต้องตรวจสอบด้วยคนPhase 3
Local Data Structure

3. โครงสร้างข้อมูลบนเครื่อง (Local Data Structure)

ทุกตารางข้อมูลที่กรอกในพื้นที่ (เช่น feeding_record, harvest_record) ต้องมีฟิลด์เสริมเหล่านี้เพิ่มจากฟิลด์ปกติที่ spec ไว้ในแต่ละโมดูล

ฟิลด์เสริมที่ทุกตาราง local ต้องมี

เพิ่มเข้าไปในทุกเอนทิตีที่พนักงานภาคสนามกรอกได้แบบออฟไลน์ (นอกเหนือจากฟิลด์ธุรกิจปกติที่ spec ไว้ในโมดูลนั้น ๆ)

ฟิลด์ชนิดข้อมูลเก็บอะไร
local_uuidข้อความ (UUID, สร้างที่เครื่อง)รหัสเฉพาะของเรคคอร์ดนี้ สร้างตอนออฟไลน์ก็ได้ ไม่ชนกับเครื่องอื่น
server_idเลขอ้างอิง (ว่างได้จนกว่าจะ sync สำเร็จ)รหัสที่เซิร์ฟเวอร์ตอบกลับมาหลัง sync ครั้งแรกสำเร็จ
sync_statusตัวเลือกคงที่ (enum)เลือกได้เฉพาะ: pending, synced, failed
created_at_localวันเวลา (timestamp)เวลาที่เครื่องมือถือบันทึกไว้ ณ ตอนกรอก (ใช้แสดงผล ไม่ใช้ตัดสิน conflict)
synced_atวันเวลา (timestamp, ว่างได้)เวลาที่ sync ขึ้นเซิร์ฟเวอร์สำเร็จจริง
retry_countตัวเลข (int)จำนวนครั้งที่ลอง sync แล้วไม่สำเร็จ ใช้ตัดสินใจ backoff/แจ้งเตือน

sync_queue

คิวงานที่รอส่งขึ้นเซิร์ฟเวอร์ — แยกจากตารางข้อมูลจริง เพื่อให้ควบคุมลำดับ/สถานะการส่งได้อิสระจากตัวข้อมูล

ความสัมพันธ์: อ้างอิง local_uuid ของเรคคอร์ดในตารางข้อมูลจริงที่ต้องซิงค์

ฟิลด์ชนิดข้อมูลเก็บอะไร
target_tableข้อความ (text)ชื่อตารางข้อมูลที่ต้องซิงค์ เช่น "feeding_record"
target_local_uuidข้อความ (UUID)เรคคอร์ดไหนในตารางนั้นที่ต้องส่ง
operationตัวเลือกคงที่ (enum)เลือกได้เฉพาะ: create, update, delete
idempotency_keyข้อความ (UUID, สร้างครั้งแรกที่เข้าคิว)กันส่งซ้ำสร้างข้อมูลซ้ำ ถ้า retry ต้องส่ง key เดิมทุกครั้ง
queued_atวันเวลา (timestamp)เวลาที่เข้าคิว ใช้เรียงลำดับการส่ง (เก่าไปใหม่)
Conflict & File Handling

4. การจัดการข้อมูลขัดแย้งและไฟล์ (Conflict & File Handling)

เกิดขึ้นเมื่อพนักงานหลายคนแก้ข้อมูลเดียวกันตอนออฟไลน์พร้อมกัน แล้วมาซิงค์ชนกันทีหลัง

ข้อมูลทั่วไป (บันทึกกิจกรรม)

  • ใช้ Last-Write-Wins เทียบด้วยเวลาเซิร์ฟเวอร์ (ไม่ใช่เวลาเครื่อง) เรคคอร์ดที่ sync ถึงเซิร์ฟเวอร์ก่อนแต่เวลาบันทึกจริงทีหลัง ยังชนะได้ถ้าเวลาบันทึกจริงใหม่กว่า
  • เหมาะกับข้อมูลเช่น feeding_record, care_task ที่แก้ไขซ้อนกันไม่กระทบความถูกต้องทางบัญชี

ข้อมูลอ่อนไหว (การเงิน/สต็อก)

  • ห้ามใช้ Last-Write-Wins เงียบ ๆ — ให้ flag เป็น conflict แล้วเก็บทั้งสองเวอร์ชันไว้ให้แอดมินเลือกด้วยคน
  • ใช้กับ stock_movement, payment, journal_entry ที่ overwrite ผิดพลาดกระทบเงินจริง

รูปภาพ/ไฟล์ที่ถ่ายในพื้นที่

  • เก็บไฟล์ไว้ใน local storage ของเครื่องก่อน พร้อม path อ้างอิงในเรคคอร์ด
  • อัปโหลดขึ้น Azure Blob Storage เฉพาะตอนออนไลน์ อัปเดต path เป็น URL จริงหลังอัปโหลดสำเร็จเท่านั้น
  • ห้ามลบไฟล์ local ทิ้งจนกว่าจะยืนยันว่าอัปโหลดสำเร็จแล้ว
Developer Checklist

5. Checklist สำหรับ Dev

สิ่งที่ต้องทดสอบจริงก่อนปล่อยฟีเจอร์ offline ทุกครั้ง — เน็ตในพื้นที่ฟาร์มไม่เสถียรกว่าออฟฟิศมาก ทดสอบเฉพาะกรณีเน็ตดีไม่พอ

สถานการณ์ทดสอบสิ่งที่ต้องตรวจสอบ
เปิด airplane mode แล้วกรอกข้อมูลบันทึกสำเร็จ แสดงสถานะ "รอ sync" ถูกต้อง
เน็ตหลุดกลางการส่ง syncretry ได้เองโดยไม่สร้างข้อมูลซ้ำ (เช็ค idempotency_key ทำงานจริง)
ปิดแอปกลาง sync แล้วเปิดใหม่sync_queue ยังอยู่ครบ ไม่หายไปกับการปิดแอป
สองเครื่องแก้เรคคอร์ดเดียวกันตอนออฟไลน์conflict ถูกจัดการตามกฎที่กำหนด ไม่มีข้อมูลหายเงียบ ๆ
ถอดปลั๊ก/แบตหมดกลาง syncข้อมูลใน local DB ไม่พังหลังเปิดเครื่องใหม่ (SQLite transaction ปลอดภัย)
ใช้งานต่อเนื่องหลายวันแบบออฟไลน์sync_queue ไม่ล้นจนแอปช้า/พื้นที่เครื่องเต็ม
Critical Rules

6. กฎสำคัญที่ต้องยึด (Critical Rules)

ตรรกะที่ dev ต้อง implement จริงเบื้องหลังกลไก sync ทั้งหมด

สร้าง ID แบบออฟไลน์ปลอดภัย

Phase 1

ห้ามใช้ auto-increment integer สำหรับเรคคอร์ดที่สร้างตอนออฟไลน์ เพราะสองเครื่องอาจสร้างเลขชนกัน

record.local_uuid = generate_uuid_v4()  // สร้างตอนกรอกฟอร์ม ไม่ใช่ตอน sync
server_id = null  // จนกว่า sync ครั้งแรกสำเร็จ
API ตอบกลับ server_id -> อัปเดตกลับเข้า local record

ป้องกันการ Sync ซ้ำ (Idempotency)

Phase 1

ทุก request sync ต้องส่ง idempotency_key เดิมซ้ำได้อย่างปลอดภัยถ้าต้อง retry

ที่ฝั่ง API:
  ถ้า idempotency_key นี้เคยประมวลผลสำเร็จแล้ว
    -> ตอบผลลัพธ์เดิมกลับไปทันที ไม่สร้างเรคคอร์ดใหม่ซ้ำ
  ถ้ายังไม่เคยเห็น key นี้
    -> ประมวลผลตามปกติ แล้วบันทึก key ไว้

ลำดับการส่ง Sync

Phase 1

ส่งตามลำดับเวลาที่เข้าคิว ไม่ใช่สุ่ม เพื่อรักษาลำดับเหตุการณ์ทางธุรกิจให้ถูกต้อง

sync_queue ORDER BY queued_at ASC
ส่งทีละรายการ (หรือ batch ตามลำดับ) จนครบคิว
ถ้ารายการใดล้มเหลว -> หยุดที่รายการนั้น ไม่ข้ามไปส่งรายการถัดไปก่อน
  (กันกรณีรายการถัดไปอ้างอิงรายการที่ยังไม่สำเร็จ)

Retry แบบ Exponential Backoff

Phase 2

กันไม่ให้แอปยิง request รัว ๆ ตอนเน็ตแย่ ๆ จนแบตหมด/เปลืองดาต้าโดยไม่จำเป็น

retry_delay = min(2^retry_count วินาที, 5 นาที)
ถ้า retry_count > 10 ครั้งติดกัน
  -> sync_status = failed, แจ้งเตือนผู้ใช้ให้ตรวจสอบเอง

เกณฑ์เลือก Last-Write-Wins vs Manual Conflict

Phase 1

ตัดสินตอนออกแบบตาราง ไม่ใช่ตัดสินสด ๆ ตอน implement

ถ้า target_table อยู่ในกลุ่ม การเงิน/สต็อก/สุขภาพ-วัคซีน
  -> conflict ต้องถูก flag ให้คนตรวจสอบ ห้าม auto-overwrite
ถ้า target_table เป็นบันทึกกิจกรรมทั่วไป (feeding, care_task)
  -> ใช้ Last-Write-Wins เทียบด้วยเวลาเซิร์ฟเวอร์ได้
